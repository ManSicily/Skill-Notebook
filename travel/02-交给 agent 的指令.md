# 交给 agent 的施工指令

> **给 AI 助手看的。** 用户会把这个包里的几份文件一起发给你。
> 这份指令里的每一条「必须」，都是真实项目里踩过坑之后定下来的，不是风格偏好。
> 照做能省掉一轮返工；跳过会在用户真机上出问题。

## ⛔ 先读这段：15 条红线

**如果你只读一段，读这段。**

下面这些不是"最佳实践建议"，是**真实项目里逐条踩出来的**。写的时候你的默认习惯恰好会撞上它们 ——
每一条后面都写着「破了会怎样」，以及正文里展开的位置。**拿不准就照着写，别自由发挥。**

| # | 不许做什么 | 破了会怎样 | 详见 |
|---|---|---|---|
| 1 | 不许给「住宿」「打包清单」这类派生页**另存一份数据** | 两边不一致：删了行程里的，住宿页还在；改了一边另一边不跟。用户会当成 bug 报给你 | 第 2 步 · 搜「决定二」 |

| 9 | 不许把口令、密钥写进代码或配置文件 | 交付物里带明文凭证 = 泄露。一律走**环境变量 / 占位符**，并告诉用户上线前要填 | 文末 · 搜「交付要求」 |
| 10 | 不许「测试全绿」就宣布完成 | 没做**对照实验**（把修复关掉、相关断言要变红）的绿灯是假的；测试里一整段静默跳过也会显示全绿 | 第 4 步 · 搜「提高测试可信度」 |
| 11 | 不许只跑模拟测试（像 jsdom）就算验过手机端 | 真实 CDN、真实视口、真实键盘、真实缓存投递，模拟环境一样都测不出来。**必须另开真浏览器 + 移动视口** | 第 4 步 · 搜「真机验证不能省」 |
| 12 | 不许用「发布成功」代替「线上是对的」 | 部署返回成功 ≠ 用户拿到的是新代码。要三层核对（拉线上文件 diff / 连探不跳版本 / 真浏览器跑线上） | 第 2 步 · 搜「发布成功 ≠ 线上是对的」 |
| 13 | 不许自己判断「用户不需要这个」 | 用户列的清单**不得删减**。定不了就先问一句，别闷头替人决定 | 「通用规矩」· 搜「别替用户做决定」 |
| 14 | 不许只验证「读得通」就以为云数据库配好了 | 写权限是**另一道门**。读得到、写不进，而界面还显示"已同步"（假象）→ 用户改的东西**一直没上去**，几天后才发现 | 第 3 步 · 搜「能读」 |

## 你的任务

帮用户做一个**手机端的旅行行程应用**，形态是纯静态 PWA，可选带多人协同。

三件事，按顺序做，**每做完一件事停下来给用户看**：

1. 先把路线规划出来（用户确认了才继续）
2. 再搭应用（先给能跑的最小版本，再加功能）
3. 最后自己验收一遍（按 `03-交付后怎么验收.md` 里的清单自测）

---

## 第 0 步：先确认，别急着写代码

用户的填写可能很粗（「成都周边，5 天，2 人」）。**不要自己脑补细节直接开工**，先把下面这几件事问清楚 —— 一次问完，别挤牙膏：

1. 出发日期定了吗？没定的话按「大概什么时候」排
2. 几个人、什么关系（决定住宿怎么排、节奏怎么定）
3. 有没有已经定死的事（必须某天到家、已订好的票/房）
4. 要不要多人协同（这决定后面要不要开云服务，是架构级分叉）

**只问这四类。**预算、住哪、吃什么、玩什么，你自己想办法给方案，不要反过来让用户做作业。

## 第 1 步：规划路线

### 产出要求

- **按天排**，每天有：日期、主题（一句话概括这天干什么）、里程或通勤时间、当天的点（时间 + 地点 + 干什么 + 为什么去 + 花费参考）
- **给折扣/错峰设计**：节假日出行必须标出哪几天是高峰、怎么避
- **给取舍方案**：预算给完总额后，附上「超了可以砍哪个」（每项写清省多少钱）
- **留缓冲日**：行程最后留一天机动，什么都不排
- **给待办**：需要提前抢票/预约的事，写成清单，带上时间点

### 几个排路线时的硬要求

| 要求 | 为什么 |
|---|---|
| 每天给一个「强度」指标 | 长里程日和高强度景点日要错开，别连着两天把人累死 |
| 到达和离开的大交通单独标出来 | 这两段最容易被忽略，但最影响当天能不能安排景点 |
| 价格一律标「参考价 + 查询时间」 | 用户拿三个月前的价格去结账会出问题 |
| 免费但要预约的地方单独提醒 | 比如「免费但要提前 N 天抢票」—— 这类最容易漏，漏了就白跑 |
| 不确定的（营业时间、评分、距离）显式写「待核实」 | 不许编。宁可标不确定，也不要给一个看起来很像真的假数据 |

## 第 2 步：搭应用

### 技术形态（不要换）

| 项 | 用什么 | 为什么 |
|---|---|---|
| 形态 | 纯静态网页 + PWA 清单 | 不需要安装、不需要审核、能加到手机桌面 |
| 离线 | Service Worker 缓存外壳 | 高速上、山里没信号也能看行程 |
| 本地存储 | localStorage 存数据 + IndexedDB 存照片 | 照片太大了，localStorage 装不下 |
| 不用 | 任何需要构建步骤的框架 | 用户不懂技术，改起来要能直接改文件、直接发布 |
| 多人协同（可选） | 云服务的数据库 + 邮箱登录 | 没有更好的免运维方案 |

### 页面结构（默认这 6 个）

| 页面 | 干什么 | 能不能砍 |
|---|---|---|
| 今日 | 倒计时、今天的行程点、当天的天气、待办、打包清单 | 不能 |
| 行程 | 按天列出所有点，能增删改、能拖拽排序 | 不能 |
| 住宿 | 每天住哪、订没订、多少钱 | 用户勾了才做 |
| 交通 | 每段怎么走、多远、什么时候出发 | 用户勾了才做 |
| 费用 | 总花费、人均、谁该转给谁、按类型统计 | 用户勾了才做 |
| 设置 | 成员、导航偏好、备份导入导出、多人协同开关 | 不能 |

### ⚠️ 四条必须一次做对的架构决定

这四条做错了，后面要重构。**先想清楚再动手。**

#### 决定一：数据只存一份

**行程点（stop）是唯一的数据来源。**住宿页、交通页**不存自己的数据**，而是从行程里「类型 = 住宿 / 交通」的点**算出来**显示。

```
数据结构（示意）
data.days = [
  { date, theme, stops: [
      { id, time, type, name, note, price, expense, city, address, booked, ... }
  ]}
]
type 的取值：交通 / 景点 / 吃饭 / 住宿 / 活动 / 购物 / 其他
```

**反面案例（真实踩过）**：住宿页自己也存了一份住宿数据。结果是「在住宿页删了一间，行程里那条还在」—— 同一条数据要删两次；改了一边另一边也不会变。返工两次才理顺。

**成本**：一开始就这么设计，多花二十分钟。事后改，要写数据迁移。

#### 决定二：派生视图 ≠ 只读

「不存数据」不等于「不能在这页改」。

正确做法：**住宿页点一条，就地弹出编辑框，保存写回那个行程点**，页面不跳走、滚动位置不动。

**反面案例**：一开始把「这两页不存数据」翻译成了「这两页不许编辑，只能跳去行程页改」—— 用户每改一个房价都要被甩到另一个页面，改完还要自己切回来，滚动位置全丢。这是把**架构约束当成了交互约束**。

#### 决定三：费用只记在一个地方

费用记在**行程点自己身上**（住宿的费用就在那一晚那条上）。汇总时跳过派生的视图，不要两边各算一次。

同一个取舍原则：**账**不重复算，**改**的口子可以有好几个。

#### 决定四：行程内容不许写进代码

界面上出现的**任何地名、人名、价格**，都必须来自数据文件。代码里只准出现「通用词」。

**为什么**：你做的第一趟行程很可能会被复用（换个目的地再来一趟），也可能给别人用。只要有一处地名写在代码里，换数据时它就留在界面上 —— 而且它不报错，只会安静地显示上一趟的地名。

**真实案例**：一份现成应用在换掉行程数据后，首页还写着上一趟的出发地、交通页分组标题还写着「去程（A → B 方向）」、查天气用的城市坐标表里还预置着上一趟路过的六个城市、输入框示例里还留着上一位用户的昵称。数据文件已经全换了，这些照样显示。

**具体要守的**：

- 出发提示这类文案，从数据里推（例如从行程备注里取起终点），不要写死
- 「去程 / 途中 / 返程」用通用词，别加具体城市
- 需要城市坐标（查天气用）就做成一张可编辑的表，让使用者自己加城市
- 输入框的示例文字（placeholder）用中性内容，别用真实地名、真实人名、真实价格

**怎么验**：把数据文件整个换成一份完全不相干的行程（换个省份、换个人名），界面上不该残留任何旧地名、旧人名。

### ⚠️ 手机端必须做的事

这些在电脑浏览器上全看不出来，只有真机会暴露。

#### 输入框字号必须 ≥ 16px

```css
/* 全局兜底，别只改某个类 */
input, textarea, select { font-size: 16px; }
```

**为什么**：iOS Safari 在聚焦字号小于 16px 的输入框时，会**强制把整个页面放大**。而 `maximum-scale=1` 在 iOS 10+ 已经基本失效。后果是「整个页面能上下左右乱拖」，你再怎么写 `overflow-x:hidden` 都拦不住。

> 真事故：同一条反馈「弹窗还能左右滑」来了两次。第一次修的是表层（补 `overflow-x:hidden`），第二次用真实浏览器逐状态量溢出、发现布局层溢出为 0，才顺藤摸到这条。**同一个 bug 被反馈两次，就该换量具而不是再猜一次。**

#### 锁横向要显式写

```css
.scroll-area {
  overflow-y: auto;
  overflow-x: hidden;      /* ← 必须显式写：只写 overflow-y 时，另一个轴会自动变成 auto */
  overscroll-behavior: contain;
  touch-action: pan-y;
}
```

#### 改字段用「原位替换」，不要在卡片下面长出一行

点名称/备注 → **那行字自己变成输入框**（点哪写哪，改完回车即落，文字变回去，卡片高度几乎不动）。

**不要**在卡片下方追加一整行编辑区 —— 点的位置和输入的位置不在同一处，而且软键盘弹起来会把输入框顶到屏幕外。

#### ⚠️ 软键盘：整页的尺寸基准必须换成「看得见的那块」，不是 dvh

**这是真事故**（用户原话：「键盘上弹把编辑框往上挤，我下拉的时候没有反应，等于上面半个备注栏的文字我是看不到的」）。三层原因，缺一层都修不干净：

**① `100dvh` 和 `position:fixed` 都不跟软键盘走。** `dvh` 是**布局视口**高度，软键盘不改变布局视口 —— 键盘顶上来时页面还以为自己有整机那么高。iOS 为了让光标可见，会去**平移可视区**（`visualViewport.offsetTop` 变成非 0），结果"上面一截被推到屏幕上方，拖不回来"。

**② 全站只有一个尺寸基准：`visualViewport`。**

```js
const vv = window.visualViewport;
const base = Math.round(window.innerHeight);              // 布局视口高度
const vh = vv && vv.height ? Math.round(vv.height) : base; // 看得见的高度
const top = vv && vv.offsetTop ? Math.round(vv.offsetTop) : 0; // 可视区在布局视口里的偏移
const kb = Math.max(0, base - (top + vh));                 // ⚠️ 可见带【下方】还剩多少（提示条据此落位）
// ↑ 别把它当"键盘物理高度"（那是 base - vh）；平移后两者差一个 top
const kbOn = kb >= 180 || top > 0;   // 地址栏伸缩只有 ~70px，别误判成键盘
```

键盘态把这些写进 CSS 变量（`--vvh` / `--vvt` / `--kb` + `html.kb-on`），**键盘一收就撤干净**交回 `100dvh`（不撤的话地址栏一伸一缩页面会来回抽）：

```css
#app{height:var(--vvh,100dvh);top:var(--vvt,0)}          /* ← top 不能省！ */
.mask,.detail,.gate{position:fixed;inset:0;height:var(--vvh,100dvh);top:var(--vvt,0)}
.toast{position:fixed;bottom:calc(var(--tab-h) + 30px + var(--kb,0px) + env(safe-area-inset-bottom))}
```

**⚠️ `#app` 是流内元素（`position:relative`），不加 `top:var(--vvt,0)` 就不会跟平移，整块被推出屏幕上方。** `fixed` 层同理都要带（fixed 相对**布局视口**定位）。**这条纯靠 jsdom 想不到，必须上真浏览器跑一次"可视区被平移"的场景才会暴露。**

**③ `overflow:hidden` 的输入框：代码能移它、手指移不动它。** 长文本备注框如果跟着内容长高（`height=scrollHeight`），能长到 1125px 而可视区只有 508px —— 既超出屏幕又拖不动，"下拉没反应"就是字面意思。必须：

```css
.inplace.ta{overflow-y:auto;overflow-x:hidden;max-height:calc(var(--vvh,100dvh) - 150px)}
```

并且在**键盘一顶上来时按新可视区重收一次**（不收的话"框自己"就比屏幕高，滚谁都没用）。

**④ 露框要按"可视带"算** = 可视区 ∩ 滚动容器自己的矩形，交一堆后上下各留 12px。只比 `vv.height` 是错的（漏了 `offsetTop`，也不管容器边界）。键盘是**动画着上来的**：140ms / 380ms 各校正一次（只量一次会正好量在动画中间）。`visualViewport` 的 `resize` **和** `scroll` 都要听（后者是平移的唯一信号）。

**怎么验**（这类问题 jsdom 算不出真实布局）：真浏览器 + `Object.defineProperty` 换掉 `visualViewport`（改 `height`/`offsetTop` 并触发 `resize`）+ 盖一层假键盘 div，然后**跑矩阵**：平移 0 / 平移 200 各一次。只跑平移 0 看不出第 ② 条。判据：输入框整体落在可见带内、框高不超过可见高的 50%、`overflowY` 是 `auto`。

**一个取巧但很硬的证据**：同一场景截三张图（初始 / 滚到底 / 滚回原位），比 `md5`。如果"初始"和"滚回原位"**字节完全相同**，就说明手指怎么拖画面都没动 —— 比任何文字描述都结实。

#### 可点区域要收着给

**别做成「点哪儿都能改」。**一张卡上十来个可点热区，用户滑列表时「点着点着就进了编辑」—— 这是真实反馈里最高频的抱怨。

**推荐分法**：

| 类别 | 放什么 | 交互 |
|---|---|---|
| 高频、改动简单 | 名称、备注、金额 | 留在卡片上，点一下原位变输入框 |
| 低频 | 时间、类型、城市、地址、房价、订没订 | 只显示，不可点；要改走卡片右侧的 ✎ 打开完整编辑表 |
| 操作按钮 | ✎ 编辑 / 🧭 导航 / 📷 打卡 / ✕ 删除 / ☰ 拖拽 | 各自独立的按钮，别让整卡可点 |

**判断依据是频率**：改字段的频率远远低于滑列表的次数，而每次滑动都可能误触。

另外：**不要给空字段渲染「＋ 城市」这种虚线占位**。一个长得像按钮却点不动的东西，比什么都不放更让人困惑。

#### 打包清单这类「用户要自己增删改」的模块：三条护栏

打包清单天然是**两层**：一级是分组（证件卡类 / 衣物 / 药品 / 数码…），二级是分组里的条目（晕车药、充电宝…）。
**先跟用户确认"你说的分类是哪一层"，再动手** —— 有人说的"二级分类"是"条目下面再分一层"，有人说的就是"分组里的条目"。给个例子问最快：*"一级是药品，二级就是药品下的某某药品，对吗？"*

确认之后，**两级都要能编辑**（增 / 改 / 删，一级再加一个**调顺序**），并且必须带这三条：

**① 一切定位都走 id，不走数组下标。**
`list[ci].items[ii]` 在"能增删、还能调顺序"之后立刻就错位。每个分组给一个 `id`，取的时候**只按 id 在当前数据里找**；就地改名的提交回调也要在提交那一刻重新定位，**别信打开输入框时捕获的那个对象**（数据可能在这期间被整体换掉，写进去就成了"孤儿"，界面上永远看不见）。

**② 别写「空就回填种子」这种初始化。**
```js
// ❌ 用户把分组全删了 → 刷新 → 种子数据又灌回来，删除白做
if (!Array.isArray(d.packing) || !d.packing.length) d.packing = 深拷贝(SEED.packing);
// ✅ 只判类型，不判长度
if (!Array.isArray(d.packing)) d.packing = 深拷贝(SEED.packing);
```
新建用户走的是"用种子初始化一份"，本来就是数组，所以改这个判断**不影响首次体验**。凡是"用户能删空"的集合都要查一遍有没有这个毛病。

**③ 新增的小按钮，量一下真实可点面积（高度 ≥ 30px）。**
分组名后面那个 ✎ 如果只有两三个字宽、行高又只有 19px，手机上根本点不准。做法是**扩热区、不改视觉**：加大 `padding` 同时用负 `margin` 抵消，行高一点都不变。

#### 用户说「这个字段删掉」时：删界面，但绝不能顺手把数据删了

这是整份文档里**唯一一个改错就会真丢数据**的地方，务必照这两条做。

**第一条：一个字段的界面出口不止一处，先把它们全找出来。**

只删编辑表那一栏等于没删 —— 同一个字段往往还有卡片标签、详情页的行、别的页面正文、以及「＋ 添加」弹窗里的一栏。少删任何一处，老数据就会继续从那个口子显示出来。逐处确认（以价格字段为例）：

- 编辑表的字段定义（可能还有"按类型换叫法"的机制，如交通叫「费用参考」、住宿叫「房价参考」）
- 卡片上的标签元素
- 详情页的那一行
- 其他页面正文里的输出（如交通页每段里的价格行）
- **「＋ 添加」弹窗里的那一栏**（最容易漏，它和编辑表是两套字段列表）
- CSS 里对应的死样式（留着会让人以为出口还在）

**第二条：保存时"收不到值的字段"必须整个不赋值，不是赋空。**

```js
// ❌ 危险：界面撤了栏，保存回调照旧跑 → 用户随便改一次别的字段，老数据被清空
s2.city = String(vals.city || "").trim();        // vals.city 是 undefined → 变成 ""
Object.assign(s2, { ..., price: vals.price });   // 同理

// ✅ 正确：收不到就不碰它
if (type === "lodging") {
  s2.booked = vals.booked === "true";            // 只留还在界面上的字段
}
Object.assign(s2, { name, time, allDay, type, note });   // price 整个不出现
```

**为什么这条要单独盯**：它是**静默**的 —— 界面一切正常、测试不报错、用户当场也看不出问题，只是某天回头看老数据，那些值全变成空字符串了，而且**撤销不回来**（旧值已经没了）。

**验收时必须亲手试一次**：找一个老数据里填过这个字段的点，打开编辑表**什么都不改、直接保存**，然后去数据里确认那个值还在。不能只测"界面上看不到了"。

#### 拖拽排序

- 用 **pointer 事件**（`pointerdown/move/up`），不要用 click
- **一按就跟手**：移动 4px 或按住 180ms，任一先到就激活
- 激活时卡片**浮起来跟手指**（`position:fixed` + `translate3d`），原位留一个虚线占位块
- 拖到屏幕上下边缘要**自动滚动**
- **松手后必须拦掉浏览器自动合成的那一次 click**（用捕获阶段 + 600ms 兜底自愈），否则会误触发折叠列表、误进详情页
- 排序完**只落盘、不整页重渲染**，否则用户看到「当天列表折回去了」，感觉像白拖了
- 监听器要**全局单例**，别每个卡片都往 window 上挂一遍（挂了上百个永不失效的监听器，越用越钝）

### ⚠️ 缓存与发布（不做这套，用户永远看到旧版本）

**静态资源一律带版本号，版本号只有一个来源。**

```
index.html      里引用的每个资源   →  app.js?v=1.2.3
Service Worker  的缓存名          →  带版本号
Service Worker  的预缓存列表每一项  →  都带 ?v=
PWA 清单里的入口地址              →  带 ?v=
图标文件                          → 也要带（最容易漏）
```

**硬规则：内容变了就升版本号。**地址不变、内容变了的话，被缓存的旧文件纹丝不动 —— 用户会一直看到旧版，而且怎么刷新都没用。

**反面案例**：改完 PWA 清单忘了升版本号 → 实测带版本号那份还是旧的（469 字节），不带参数的才是新的（478 字节），差的 9 字节正好是 `?v=` 那一段。

**版本号要能被用户自己看见。** 在设置页最底下一行写出版本号（`v1.2.3`），并且告诉用户：
**打开后先下拉刷新一次，再去设置页底部确认版本号**。不然用户永远分不清自己看的是新版还是缓存里的旧版，
你也没法在电话里问清"你那边显示多少"。

### ⚠️ 发布成功 ≠ 线上是对的

平台的部署命令返回成功，只说明**文件传上去了**，不说明**用户拿到的是新版**。
这两件事之间隔着 CDN、缓存、域名、Service Worker 四道门。所以每次发布都要走完下面三层，
**缺一层就等于没核对**：

#### 第一层（发布前）：拉线上文件下来，跟本机逐条对 —— 不凭记忆

要回答的是「**我这次到底要推什么**」：

```bash
# 把线上当前文件拉下来（带线上正在用的版本号）
for P in index.html app.js seed.js sw.js manifest.webmanifest; do
  curl -s "$BASE/$P?v=$CUR" -o "on_$P"
done
```

然后逐条看：

- **数据文件必须逐字节相同**（`cmp -s on_seed.js 本机/seed.js`）。**这一条最要紧** ——
  它证明你这次改的全是代码，没在数据上动过手脚。有差异就停下来查。
- **其余文件只该差版本号**：`diff on_sw.js 本机/sw.js`，如果差的不止版本号，说明本地有别的东西没同步。
- **统计改动量**（新增/删改各多少行），并**逐条看线上独有的行** —— 那些应该全是你有意删掉的旧代码。
  出现你不认识的行，就是有别人的改动混进来了，或者文件被谁动过。
- **实验残留自检**：`debugger` / `console.log` / `TODO` / `FIXME` 计数必须是 0。
  上线前留在代码里的调试语句，用户是看得见的。

#### 第二层（发布后）：缓存投递是不是干净

```bash
# 同一个地址连探 15~20 次，看字节数是否在跳
for i in $(seq 1 15); do printf "%s " "$(curl -s "$BASE/" | wc -c | tr -d ' ')"; done
```

字节数在跳 = 缓存投递不稳定（有时返回旧文件、有时新文件）。**必须一样**。
再对每个文件做**逐字节比对**（带版本号取），并确认四处版本号同源。

#### 第三层（发布后）：真浏览器跑线上真站点

**这一层不能省** —— 真实 CDN 加载、真实域名的 Origin 校验、真实缓存投递、真实布局引擎，
前两层一个都测不出来。用无头浏览器（移动视口 390×844 左右）打开**线上地址**，
把关键路径**在线上重放一遍**，同时收页面的 console 异常。

重放什么：用户报的那条操作路径（最优先）、以及这次改动涉及的每条主路径。

> 真事故：**844 条断言全绿**的情况下，一个线上故障是完全隐形的 —— 本地跑得好好的，
> 线上因为域名 Origin 校验和缓存投递的差异，行为不一样。

#### 收尾：把线上核对的结果归档

截图 + 每轮的断言输出 + 核对脚本，一起存进项目里（别只留在临时目录，会被系统清掉）。
下次再出问题，这就是「上一版线上长什么样」的底本。

## 第 3 步：如果做多人协同

这一步最容易出隐性故障，认真对待。

### 权限必须落在数据库上，不是前端藏按钮

用**行级安全**：每张表写清「谁能读、谁能写」。前端只是界面，不能当门。

### 四个必踩的坑

| 坑 | 现象 | 怎么避 |
|---|---|---|
| 表之间的策略互相引用 | 数据库直接报「策略无限递归」 | 用 `SECURITY DEFINER` 辅助函数断开循环 |
| 成员能改「归属者」字段 | 别人能把你的行程「抢走」 | **列级授权**：只允许改内容字段，归属字段锁死 |
| **被权限拦下的写入不报错** | 界面显示「保存成功」，实际一个字没写 | 更新返回**空数组 = 没权限**，必须显式判错并提示 |
| 邀请码可被枚举 | 6 位码 + 公开的接口 = 有被撞开的风险 | 服务端加频率限制；加入必须走服务端函数，不要放前端 |

> 第 3 条最阴：用户以为存上了，其实没有。**「静默成功」比报错危险得多。**

### ⚠️ 同步策略只能有一份（这条做错会真的丢数据）

「云端 → 本地」这条路，**通常不止一个入口**：

| 入口 | 什么时候走 |
|---|---|
| 定时轮询 | 应用开着的时候，每隔几秒 |
| **登录 / 刷新后的重连** | 每次打开、每次刷新，**必经** |

**两个入口是两段独立代码。只要有一段没判时间戳，它就是丢数据的漏口。**

> 真事故：轮询那条判了「谁的时间戳新听谁」，而刷新重连那条是**无条件用云端那份覆盖本地**。于是只要那一次推送没成功（网络不通 / 云端组件没加载出来 / 编辑那一刻会话还没恢复 / 被权限拦下），本地改动就只躺在手机上，**一刷新就被云端旧的盖掉**，改动静默消失。用户的原话是「我改了一处行程点，刷新页面后信息被重置了」。

**做法：把「谁新听谁」收成一处函数，两个入口都调它。** 判断规则两条：

1. 云端没有这份、或**本地更新** → 把本地推上去（顺序很关键：**先推，再决定要不要拉**）
2. 云端更新 → 拉下来覆盖本地

> 两条通路各写一套判断，判定不一致的那条必然成为漏口。

**顺带两条失败处理**（跟上面同一个改动里一起做）：

- **失败提示要说真话。** 只写「同步失败」，用户会读成「我刚才改的没保存」，然后白重做一遍 —— 可本地其实已经落盘了。写「**未同步·已存本机**」。
- **一次失败不能变成永久停摆。** 刷新时拉取失败就直接 `return`，后面的轮询启动会被跳过 —— 得手动再刷新一次才恢复同步。**失败路径也要把轮询起起来。**

> 上线前必须真机走一遍：**改一处 → 刷新 → 改动还在吗**。这一关不做，"丢了数据"要等用户自己发现。

### ⚠️ "能读"不等于"能写"（云端权限有两道门，最容易漏一道）

数据库上管权限的是**两道独立的门**：**表级授权**（这个角色能不能碰这张表）→ **行级安全策略**（能碰哪些行）。
两道门的"拒绝"长得完全不一样：**行级策略**拦下来是**静默的**（不报错，返回空数组）；而**表级授权**没给会**直接报错**。

所以会存在一种极隐蔽的坏状态：**读一直是好的，写从来没成功过。**

> 真事故：建表时给了「查询、新增、删除」三种权限，**唯独漏了「修改」**。于是——
> - 每次"把改动推上云端"都失败，界面上只有一枚小徽章写着「同步中断」；
> - 而**读是通的**，所以界面看上去同步在工作；
> - 云端那条记录的"创建时间"和"更新时间"**一模一样**，三天里一个字节没变 —— 所有人的改动都只躺在各自手机上。
>
> 教训：**只读能跑通的多端协同，看起来像协同在工作。** 用户可能几天后才发现"我改的东西对方看不到"。

**要做两件事：**

1. **给表配权限时，四种操作逐个列出来对**：查询 / 新增 / 修改 / 删除。一行写成列表最容易漏「修改」。
2. **自检别只测读**：如果应用有连接自检，让它覆盖**一次写**（哪怕是一条无害的写）。
   一条只测"读"的自检，在"写权限缺了三天、所有同步都失败"的环境里会**一路绿灯**。

### ⚠️ 弹窗打开着的时候，数据可能被整个换掉（保存会写到"孤儿"上）

**这一条做错的表现很迷惑人**：用户说「我怎么编辑都没用，一保存就变回默认值」。
**只改一个字段和改全部字段结果完全一样** —— 因为整个保存回调都写在一个**已经不在数据里的对象**上。

**病因**：编辑弹窗打开的那一刻，代码抓住了那条记录：

```js
const s = data.days[i].stops[j];        // ← 抓住的是"那一刻"的对象
openSheet(字段, 值 => {
  Object.assign(s, 值);                 // ← 保存时往它身上写
});
```

而只要这中间**数据被整个换过**（云端拉回来一份、从备份恢复、重新读了一遍），
`data.days[i].stops[j]` 就已经是**另一个对象**了。往旧对象上写：**不报错、不抛异常，
就是界面上永远看不见**。

**为什么会发生**：任何"把数据整体赋一遍"的地方都会造成 —— 云端同步拉取是最常见的那个。

**根治**：**保存时按 id 重新找一遍**，不许信打开时抓的那个。

```js
/* 只按"这条记录的 id"在当前数据里找 —— 不要假设"第几天/第几条"的位置也没变 */
function locateStop(sid) {
  for (let i = 0; i < data.days.length; i++) {
    const d = data.days[i];
    for (let j = 0; j < d.stops.length; j++) {
      if (d.stops[j].id === sid) return { dayIdx: i, stopIdx: j, d, s: d.stops[j] };
    }
  }
  return null;
}

// 保存回调开头：
const loc = locateStop(s.id);
if (!loc) { toast("这条已经不在了（可能被同行删掉了）"); return; }
const s2 = loc.s;                        // ← 此后一律用它
```

**三条配套纪律**：

1. **所有"打开弹窗 → 保存"的地方都要改**。有一条没改，那条路就会丢内容。
2. **弹窗里顺带抓的其他记录也要重新找**。例：这个应用里有「同一段住宿其余几晚也记同样金额」的
   功能，它在弹窗打开时抓了另外几晚的引用 —— 那几晚同样是孤儿，钱会抄到一堆看不见的地方。
3. **别用"编辑时先不同步"来代替重新定位**。那个只能挡住常规路径（换页、重新登录、
   从别处进来照样踩），它能解决"打断编辑"，但**不能解决写错对象**。两件事都要做。

### ⚠️ 推送成功 ≠ 事情结束（少做一步，应用会自己跟自己打乒乓球）

「谁的时间戳新听谁」这个规矩里，**推送成功后必须把本机版本号对齐到推送时刻**。
不对齐，下一轮就会拿云端时间戳跟本机**旧**版本号比，判成「云端更新了」，
把**自己刚推上去的那份**原样拉回来、重建界面、还弹一句「已同步同行的更新」——
推完拉、拉完推，停不下来。

> 真事故：用户报「编辑的时候老是弹出『已同步同行的更新』，打断我正在改的内容」。
> 实测连跑 10 轮弹 5 次（应用里每 5 秒一跳，约每 10 秒打扰一次）。

**四处都要做，缺一处就还在打乒乓球：**

1. **落盘分两档**：本机产生新内容 → 版本号 = 现在；**采纳云端版本 → 版本号留在云端那个时间戳上**。
   用同一个函数干这两件事，版本号必然被来回推着走。
2. **推送成功后，把本机版本号对齐到推送时刻**（那个时刻才是"两边共同的最新版本"）。
   有两条推送路径（新接口 / 老接口）就改两条 —— 别只改一条。
3. **判断"内容变没变"别用 `JSON.stringify(新) !== JSON.stringify(旧)`**。这个写法有两处必错：
   数据里带着版本号字段（每轮都在动）、服务端 jsonb 会**重排键序**（同一份内容也比不相等）。
   结果这个比较**永远为真** → 每次都重建界面、每次都提示。要**按键名排序、并抹平版本号字段**再比。
4. **用户正在编辑时，让路**。这一条最容易漏，也最伤 ——
   用户说"打断我正在编辑的内容"，**被打断的不是那个提示**：重建界面会把
   **还没提交的输入连同焦点一起冲掉**。判断"在编辑"的四个信号：有弹窗开着 / 有详情页开着 /
   有没提交的原位输入框 / 焦点在输入控件上。任一命中就**这一跳先不动**，下一跳再拉。
   **不能"先换数据、稍后再画"**：数据一换，用户手上这次编辑的落点就变了。

**验收**：编辑一处 → 连跑 10 轮 → **零提示、零多余推送**；再让"同行"真改一次 →
**该拉的照样拉到、提示一次**（让路不等于不同步）。

### 错误文案要带「出在哪一步」

同一个认证错误码，在不同步骤含义完全不同：

- **发验证码**那一步报 401 → 只可能是**配置/密钥问题**（那一刻根本还没有会话，不可能是「登录过期」）
- 已经登录后的 401 → 才可能是会话过期

把「凭据无效」笼统说成「登录状态失效了，请重新登录」，会把用户和排查者一起引偏方向。

> 真事故：一个密钥少抄了一个字符（31 位 vs 32 位），所有请求 401。但错误文案说的是「登录状态失效」，让人往「会话过期」查了很久。**假报错比没报错更危险。**

### 逃生出口

凡是全屏的、拦住用户的界面（登录、引导、付费墙），**必须留一条无条件可达的退出路径**：

- 不要用原生确认弹窗（装到桌面后是独立应用模式，某些环境下弹窗会被静默拦掉，按钮看着在、点了没反应）
- 退出后要**真的落在该去的地方**（「重画某个页面的内容」不等于「切到那个页面」）
- 逃生路径要测过：故意从别的页面唤起来，再退出，看落在哪

### 一个前端性能陷阱

```js
async function commit() {
  save();
  if (有远端要推) await push();   // ← 只有真有远端时才 await
  render();                        // 否则这一行会被推到下一个微任务
}
```

无差别加 `await` 会把本地模式也拖成异步 —— 表现是「点完保存，界面慢半拍才变」。用户说不清哪里不对，但手感就是差。

## 第 4 步：测试

**不要只交功能。**每修一个 bug，就把那个 bug 的**症状**写成一条断言，防止下次改别的地方又改回去。

### 提高测试可信度的几条做法

**1. 末尾哨兵**

如果测试体整个包在一个大 `try` 里，中间任何一处提前抛异常，**它之后的所有断言会一起消失**，而输出依然是「全部通过」。

修法：在 `try/catch` **外面**加一条断言，检查实际跑过的断言条数：

```js
// 必须在 try 外面，否则它自己也会被跳过
check(`共跑了 ${count} 条断言（低于 ${MIN} 说明中间有段落被静默跳过）`, count >= MIN);
```

**2. 对照实验**

改完之后，**把修复关掉，看测试会不会红**。

不会红 = 这条断言没抓住东西，等于没测。

> 真事故：一条测试偶发少跑了一截，而少掉的那个数字**正好等于某个历史版本的总数** —— 不是随机数，说明是整段被跳过了。别急着归因「环境问题」，先对比这个数字。

**3. 别让测试自己骗自己**

AI 写的测试最容易在这两处造假绿：

**假后端存了引用。** 模拟云端时，存下来的数据**必须深拷贝**：

```js
// ✗ 错：存的是应用里那个活对象。应用再改一次，这份"云端数据"跟着一起变
S.row = { payload: st.payload.payload };
// ✓ 对：真服务器是走 JSON 过网的，两边本来互不影响
S.row = { payload: JSON.parse(JSON.stringify(st.payload.payload)) };
```

> 真事故：复现「改完刷新丢数据」时，第一版假后端就栽在这里 —— **「云端那份」跟着本地一起变，怎么写都对**，跑出来「改动保住了」，差点把结论反过来。

**别读「调用记录里的对象」。** 那也是活引用 —— 一旦代码里 `data = 新对象` 重新赋值，记录里那个引用仍指向**旧对象**，于是「到底推没推上去」会被它答成「推了」。

要问就问**服务端收到的那份**：让假后端在收到的当下深拷贝存一份，断言读它。

> 这条是**对照实验**逼出来的：修复关掉之后，测试本该红的却绿着 —— 一查才发现，自己找了个假证人。

**4. 测试里的"差"要手动造出来（我管它叫装引信）**

如果 bug 的成因里带着**两个几乎同时发生的量之间的差**（时间戳、序号、请求顺序），
这个差在测试环境里**常常是 0**，真机上**必然不是 0**。差为 0 时 bug 不发作 ——
于是你"复现 → 修 → 加断言 → 对照组验证"全套做下来，**新断言在老代码上也是绿的**，
你会以为自己在修一个不存在的问题。

> 真事故：修"自己跟自己同步"时，罪魁是落盘与推送时刻之间那 1~2 毫秒。测试环境里这俩
> 经常落在同一毫秒 —— 第一版断言在旧代码上**假绿**了两条。把云端时间戳显式挪后 5ms 之后，
> 旧代码才如实变红。

三条纪律：

1. **给引信本身写一条断言**（"前提：云端时间戳晚 5ms，引信已装上"）。它没装上时，
   后面的断言全变成空转，而且**表现为绿的** —— 这种假绿比红更难查。
2. **对照组必须跑**：把修复还原，跑一遍。该红的没红，就是场景没造真。
3. 换环境（本地 → 真机 → 别处）之后，**重新问一遍"这个差在这里是不是 0"**。

**5. 对照实验必须「一次只还原一处」**

想知道「这条断言到底在守哪个改动」，就得把修复还原回去看它变红。
但**一次只还原一处** —— 把好几处一起还原，会出现**级联**：A 处的还原让数据变脏，
B 处的断言跟着抛异常，于是一下红 20 条，**你根本分不清哪条对应哪处**，实验白做。

做不到隔离时，问自己一句：**这条断言是不是依赖了别处的数据？**
真遇到过：一条断言用「城市 = 济南」去找住宿段，可合并判据早就不看城市了 ——
数据一动就 `undefined`，整段抛异常，后面几百条一起不跑，**输出还显示"全绿"**。
（这也说明**用会变的东西当定位锚点，等于给整份测试装了哑炮**。锚点要用稳定的东西：id、
序号、或这段数据本身独有的名字。）

**6. 核对脚本自己会造假失败 —— 这是最危险的一类**

脚本报红的时候，**先怀疑脚本，再怀疑代码**。三种最常见的自造红：

- **拿固定等待当"等加载完"**。`导航 → sleep(2500) → 开干` 在本地够用，
  线上过 CDN 就超时。症状是**本机永远绿、线上偶红**，现场长得特别像"新修复在线上没生效"。
  改法：**等到能被观测的事实成立才往下走**（轮询到版本号是字符串**且**主容器真的有内容），
  并**把等待耗时打进报告**。
- **元素不存在时脚本直接崩**。用户那版没有这个按钮（那是正常的对照组结论），
  可 `document.querySelector(...).click()` 一抛异常就**带走整轮**，连"过了几条"都看不到。
  改法：所有触碰页面的动作都包一层（元素不在就返回 false、数据读不到就返回 null），
  让"这一版没有这个功能"如实呈现为 ✗。
- **多轮结果不一致**。同一脚本连跑 3 轮，**关键测量值必须逐字节相同**；
  只有"等了 785ms / 1074ms"这类耗时回显该有差异 —— 那正是它在正常工作的证据。

**7. 验证结论必须自己看一眼，不能只看脚本说"全绿"**

脚本会绿着给你一张**废图**（截在前一帧、截在页首、截成空白）。
所以**给用户看的证据截图，自己核一遍再说** —— 图里该出现的字出现了吗？
两张"滚动前/滚动后"的图，内容真的不同吗？
（一个很省事的硬判据：**比较两张图的哈希**。旧版"拖不动的框"就是靠这个坐实的 ——
滚前滚后两张截图**字节完全相同**，说明手指拖下去画面纹丝不动，而这一点肉眼完全看不出来。）

### 真机验证不能省

模拟环境测不出这些：

- 真实的 CDN 加载、真实的域名校验、真实的**缓存投递**
- 真实布局引擎（横向溢出、软键盘顶起）
- 浏览器在 `pointerup` 后**自动合成 click** 的行为
- 移动端 Safari 的自动放大

**至少用真实浏览器的移动视口（390×844 左右）过一遍每个页面**，检查横向溢出、控制台异常、以及关键交互真的发出了预期动作。

**怎么做（一条能落地的路子）**：用无头浏览器 + 调试协议驱动，不需要装额外的测试框架：

```
启动无头浏览器（开启远程调试端口，用独立的临时用户目录，别动用户真实浏览数据）
  → 连上调试协议，开一个会话
  → 页面导航到目标地址
  → 【关键】导航后立刻注入错误监听（window 上的 error 事件 + console 异常收集）
       —— 这一步必须赶在应用脚本跑起来之前，晚一秒就收不到启动阶段的错
  → 轮询等到"应用真的活了"（见上面第 6 条），不要死等固定秒数
  → 设成移动视口尺寸（390×844），每次交互后重新取元素位置再断言
  → 把关键交互包成"给几次机会"（首帧布局和事件绑定有先后，一次扑空不算应用没功能）
  → 结束时打印：通过数 / 失败数 / 收到的 JS 异常列表
```

两个容易忽略的点：

- **每次交互后要重新取元素位置**再量尺寸，不能复用交互前拿到的坐标。
- **量可点面积**。手指点不准的按钮，功能测试全绿而用户用不了 ——
  真闯过这种祸：一个编辑按钮只有 **23×19px**，手机上根本点不中。
  判据：可点高度 **≥ 30px**（去美术上那点精致之前，先想想手指）。

## 通用规矩

### 别替用户做决定

不要用常识判断加限制。比如「名字里带『家』的地方不用给导航按钮」——听起来合理，但用户可能就想在路上点一下看看还有多远。

**拿不准就加上，然后问一句。**

### 兜底要兜到「还能用」

给不出精确结果时，给一个粗糙但有用的。

> 例子：导航关键词推导。是地名就用「城市 + 名称」；不是地名（「机动缓冲」「睡到自然醒」这种）就退回「城市 + 地址」；只有城市就退城市；连城市都没有才用原名。**宁可搜得糙，也不能发一个空关键词出去。**

### 说清取舍

凡是让用户「多花一步」的设计，都要说明换来了什么、代价是什么。

> 例子：把「点哪儿都能改」改成「两个明确按钮」之后，想改的时候要多瞄准一下 —— 换来的是滑列表不会误开编辑框。这个交换值不值，写清楚让用户自己判断。

### 数据要有来源标注

任何价格、营业时间、评分，标注清楚是**实时查到的**还是**静态知识**，以及查询时间。不确定就写「待核实」。

做完之后，除了应用本身，交这四样：

1. **能打开的链接**（或者本地怎么跑起来的一行命令）
2. **一份说明**：这应用有哪些功能、数据存在哪、怎么备份
3. **一份变更记录**：每次改了什么、为什么改（后面你自己和用户都要看）
4. **自测结果**：按 `03-交付后怎么验收.md` 逐条过完之后，哪几条通过、哪几条没通过
