### 派生视图：住宿页从行程点算出来

> ⚠️ **先问清楚：住宿页要「一晚一条」，还是「连住的合并成一段」？**
>
> 这是**两个独立的决定**，别混在一起：
>
> | 决定 | 该选什么 | 依据 |
> |---|---|---|
> | **数据粒度** | 一晚一条（中间换房随时能改） | 这个没有商量余地，反了要返工一整轮 |
> | **显示聚合** | 合并成段 / 一晚一条 —— **两种都合理，得问** | 合并＝一眼看清住几晚；一晚一条＝按时间顺序排的清单 |
>
> 我在这上面来回改过一次：先按"一眼看清住几晚"做了合并显示，用户后来要"按时间顺序排列" → 又改回一晚一条。
> **两次都没错，错的是把显示聚合当成粒度问题的自然结论。**
>
> 合并那一版留着当参考（粒度对、只是显示方式不同）：

```js
/* 把"连着住同一间的几晚"合并成一段显示。
   注意：不复制数据，只是算出来给页面看。 */
function deriveStays(data) {
  const stays = [];
  data.days.forEach((day, di) => {
    (day.stops || []).forEach((s, si) => {
      if (s.type !== "lodging") return;
      const last = stays[stays.length - 1];
      const samePlace = last
        && last.name === (s.name || "")
        && last.city === (s.city || "")
        && last.endIdx === di - 1;               // 必须紧接着，隔一天就不算连着住
      if (samePlace) {
        last.nights.push({ di, si, day, s });
        last.endIdx = di;
      } else {
        stays.push({
          name: s.name || "", city: s.city || "",
          startIdx: di, endIdx: di,
          nights: [{ di, si, day, s }]
        });
      }
    });
  });
  return stays;
}
```

**「一晚一条」那一版更简单** —— 按天遍历，天然就是时间顺序：

```js
/* 每晚一条：直接按天顺着取，不用合并，出来的顺序就是时间顺序。 */
function eachNight(data) {
  const out = [];
  data.days.forEach((d, di) => {
    (d.stops || []).forEach((s, si) => {
      if (s.type === "lodging") out.push({ di, si, day: d, s });
    });
  });
  return out;                          // 卡片数 === 住宿晚数
}
```

**这条顺带解释了一个好用的验证方式**：改成"一晚一条"之后，「卡片数是否等于住宿晚数」本身就是一条硬断言 ——
合并版是 12 晚 → 6 条，一晚一条是 12 晚 → 12 条，数字一对就知道实现是哪种，不用去读代码。

**为什么这么写**：用户在住宿页删掉一段，行程页必须跟着没了 —— 只有「不存第二份」能保证这点。费用汇总也不会重复算。

**容易写错的地方**：
- 一开始很容易图省事让住宿页自己存一份。等发现「两边不一致」再改，要写数据迁移
- 「不存数据」不等于「这页不能改」—— 点条目就地弹编辑框，保存写回那个行程点，页面**不跳走**（这是两件事）

## 2. 版本化的 Service Worker

**用途**：让应用能离线用；同时避免「用户永远看到旧版本」这个最折磨人的问题。

```js
/* sw.js —— 离线缓存外壳
   策略：同源 GET 请求走"网络优先、失败回缓存"（有更新时能立刻拿到新版）
   数据请求（接口、天气）直接放行，不走这里 */
const VER = "__APP_VERSION__";                   // ← 与应用其他地方的版本号同源
const CACHE = "trip-app-v" + VER;
const V = "?v=" + VER;

/* 预缓存的每一项都带版本号：换版本 = 换一批全新地址，
   平台按路径缓存的旧文件永远命中不了 */
const SHELL = [
  "index.html" + V,
  "app.js" + V,
  "manifest.webmanifest" + V,
  "icon.svg" + V                              // ← 图标最容易漏
];

self.addEventListener("install", e => {
  e.waitUntil(
    caches.open(CACHE).then(c => c.addAll(SHELL)).then(() => self.skipWaiting())
  );
});

self.addEventListener("activate", e => {
  e.waitUntil(
    caches.keys()
      .then(keys => Promise.all(keys.filter(k => k !== CACHE).map(k => caches.delete(k))))
      .then(() => self.clients.claim())
  );
});

self.addEventListener("fetch", e => {
  const url = new URL(e.request.url);
  if (e.request.method !== "GET" || url.origin !== location.origin) return;  // 云端接口放行
  e.respondWith(
    fetch(e.request)
      .then(res => {
        if (res.ok) {
          const copy = res.clone();
          caches.open(CACHE).then(c => c.put(e.request, copy));
        }
        return res;
      })
      .catch(() => caches.match(e.request)
        .then(hit => hit || (e.request.mode === "navigate" ? caches.match("index.html" + V) : undefined)))
  );
});
```

**硬规则**：**内容一变就升版本号。**地址不变、内容变了 → 被缓存的旧文件纹丝不动，用户怎么刷新都没用。

**容易写错的地方**：
- 只给部分资源打版本号（给 index 打、漏了图标或清单文件）= 留了个必踩的坑
- 版本号写死在测试里 → 每升一版都要改一堆字面量，改到第三次就有人图省事把断言删了。**从源码读出来比对**
- 换成新版本后，手机端第一次打开要**下拉刷新**一次才会换到新缓存

## 3. 云同步：谁新听谁 + 两个入口共用一套

**先说最容易翻车的地方**：往本地同步的入口**不止一个** —— 定时轮询一个，**登录 / 刷新后的重连**又一个。两个入口是两段独立代码，**只要有一段没判时间戳，它就是丢数据的漏口。**

所以把对账逻辑抽成一个函数，两个入口都调它：

```js
/* 对账：一个函数，两个入口都调。
   不要在其中一条路上另写一套判断 —— 判定不一致的那条必然成为漏口。 */
async function reconcile() {
  const remote = await pull(cfg.tripId);
  const localRev = data._rev || 0;
  const remoteRev = (remote && remote.updated_at)
    ? (new Date(remote.updated_at).getTime() || 0) : 0;

  // 远端还没有这份、或本地更新 → 推上去（先推，再决定要不要拉）
  if (!remote || !remote.payload || remoteRev <= localRev) {
    await push(cfg.tripId);
    return "push";
  }
  // 远端更新 → 拉下来
  data = normalize(remote.payload);   // ← 别人的客户端可能是旧版本存的，要过一遍归一化
  data._rev = remoteRev;
  saveLocal();
  renderAll();
  return "pull";
}
```

轮询入口（应用开着的时候）：

```js
setInterval(async () => {
  if (!session || !cfg.tripId) return;
  try {
    const how = await reconcile();
    setBadge(true);
    if (how === "pull") toast("已同步同行的更新");
  } catch (e) {
    setBadge(false, "未同步·已存本机");   // 文案要说真话，见下
  }
}, 5000);
```

刷新 / 登录后的重连入口（**这条最容易被漏掉**）：

```js
async function afterSignIn() {
  if (!cfg.tripId) { renderGate(); return; }
  let err = null;
  try { await reconcile(); } catch (e) { err = e; }
  renderGate();
  startSync();                      // ★ 无论成败都要起轮询
  if (err) {
    setBadge(false, "同步中断");
    toast("连上云端失败：" + errText(err));   // 不用写在闸门上的提示：这一刻闸门已经关了，没人看得见
    return;
  }
  setBadge(true);
  toast("已连上云端行程");
}
```

**容易写错的地方**：

- **重连那条路直接用云端覆盖本地** —— 这就是丢数据的那个 bug。轮询判了时间戳、重连没判，于是推送失败一次，刷新就把本地改动盖掉了
- **拉回来的数据必须过一遍 `normalize()`** —— 同行的人可能用的是旧版本，字段可能缺
- **失败提示要说真话**：写「同步失败」用户会读成「刚才改的没保存」，然后白重做一遍 —— 可本地其实已经落盘了。写「未同步·已存本机」
- **失败路径也要 `startSync()`**：刷新时拉取失败就 `return` 的话，轮询被跳过 → 一次失败变成永久停摆，得手动再刷新一次才恢复
- 权限被拦下的更新**不报错、只返回空数组**。不显式判的话界面会显示「保存成功」，实际一个字没写。空数组必须判成「你没有编辑权限」
- 「谁新听谁」这个策略的代价是：两个人同时改同一个点，后保存的覆盖前面的。这个取舍要在说明书里跟用户讲清楚

> **上线前真机走一遍：改一处 → 刷新 → 改动还在吗。** 这一关不做，"丢了数据"要等用户自己发现 —— 而那时改动已经回不来了。

## 4. 别让本地模式被拖成异步

```js
/* 只有真的有远端要推时才 await。
   无差别 await 会把本地模式也变成异步 —— render 被推到下一个微任务，
   用户看到的是"点完保存，界面慢半拍才变"。说不清哪里不对，但手感就是差。 */
async function commit() {
  data._rev = Date.now();
  saveLocal();
  if (hasRemote()) await afterWrite();     // ← 关键就是这一句判断
  renderAll();
}

function hasRemote() {
  return cfg.mode === "cloud" && !!session && !!cfg.tripId;
}

/* 只落盘、不重渲染 —— 拖拽排序专用。
   用 commit() 会整页重渲染：列表折回去、卡片闪一下，用户感觉像白拖了。 */
async function commitQuiet() {
  data._rev = Date.now();
  saveLocal();
  if (hasRemote()) await afterWrite();
}
```

**容易写错的地方**：这是一个**自己给自己造的回归** —— 加同步功能的时候顺手给所有写入加了 `await`，本地模式跟着变慢，而且在电脑上测不出来（因为本地测试通常没有真实的网络延迟）。

## 5. 最少转账笔数（多人 AA 结算）

```js
/* 输入：每人「应收 - 已付」的差额。
   输出：谁转给谁多少，笔数最少。
   两人时自然退化成一笔。 */
function settlePlan(members, diff) {
  const creditors = members.filter(m => diff[m.id] > 0.01)
    .map(m => ({ id: m.id, v: diff[m.id] })).sort((a, b) => b.v - a.v);
  const debtors = members.filter(m => diff[m.id] < -0.01)
    .map(m => ({ id: m.id, v: -diff[m.id] })).sort((a, b) => b.v - a.v);

  const out = [];
  let i = 0, j = 0;
  while (i < debtors.length && j < creditors.length) {
    const amt = Math.min(debtors[i].v, creditors[j].v);
    if (amt > 0.01) out.push({ from: debtors[i].id, to: creditors[j].id, amount: Math.round(amt * 100) / 100 });
    debtors[i].v -= amt; creditors[j].v -= amt;
    if (debtors[i].v <= 0.01) i++;
    if (creditors[j].v <= 0.01) j++;
  }
  return out;
}
```

**为什么从大到小排**：配对时先消化大额，剩下的零头少，笔数最少。

**容易写错的地方**：
- `0.01` 这个阈值别省 —— 不然会出现「你转给 TA 三分钱」这种毫无意义的转账
- 别写成 `if (members.length === 2)` 的分支 —— 一旦人数变成 3 个，整块结算提示就是空的

## 6. 手机端拖拽：三个关键判断

```js
/* 激活门槛：移动 4px 或按住 180ms，任一先到就激活。
   原来的实现要求"必须长按满 280ms"，用户手指已经在滑了卡片才半路开始跟，手感很钝。 */
function onPointerMove(e) {
  if (!dragging) {
    const moved = Math.abs(e.clientY - startY) > 4;
    const held = Date.now() - startT > 180;
    if (!moved && !held) return;
    activate();
  }
  moveCard(e.clientY);       // 卡片 position:fixed + translate3d 跟手指走
}

function onPointerUp(e) {
  const target = hitTest(e.clientY);          // 松手时重新算落点
  finishDrop(target);                          // ← 一定要"同步"重算，别等 requestAnimationFrame

  /* 拦掉浏览器在 pointerup 之后自动合成的那一次 click。
     不拦的话：拖完列表会莫名其妙折起来、或者误进详情页。 */
  suppressNextClick();
  setTimeout(allowClick, 600);                 // 兜底自愈，避免永远拦着
}
```

**三个容易写错的地方**：
1. **松手时落点要同步重算** —— 快速拖到别处就松手时，如果等 `requestAnimationFrame` 里的状态，会判成「没跨天」，弹回原位
2. **必须拦掉合成的那次 click** —— 浏览器会在 `pointerup` 后补一次 click，如果正好落在可折叠的标题上，列表就自己折起来了
3. **监听器挂全局单例** —— 别每张卡片都往 window 上挂一遍（挂上百个永不失效的监听器，越用越钝）

## 7. 手机端的几个必备兜底

### 7.1 字号与横向锁

```css
/* ① 输入框字号不低于 16px —— 否则 iOS 聚焦时会强制放大整个页面，

  touch-action: pan-y;
```

### 7.2 软键盘：整页尺寸基准必须换成「看得见的那块」

```js
/* 两步缺一不可：① CSS 先跟上可视区，② 控件落到看得见的区域外时再代码补滚。
   光滚没用（整页基准错了，滚到哪儿都在屏幕外），
   光改 CSS 也没用（框自己可能比看得见的区域还高）。 */

/* ---- 第一步：把"看得见的那块"量出来，写进 CSS 变量 ---- */
function viewportMetrics() {
  const vv = window.visualViewport;
  const base = Math.round(window.innerHeight || 0);       // 整机高度（键盘不改变它）
  const vh = (vv && vv.height) ? Math.round(vv.height) : base;
  /* ⚠️ offsetTop 是"可视区在布局视口里的偏移" —— iOS 为让光标可见会把可视区往上推，
        漏掉它会在最难的那一档（被平移）算错，而且本地永远测不出来。 */
  const top = (vv && vv.offsetTop) ? Math.round(vv.offsetTop) : 0;
  /* kb 的语义是「可见区下方还剩多少」，用来给浮动元素落位；
     它不是"键盘有多高"（那才是 base - vh），被平移时两者正好差一个 top。 */
  const kb = Math.max(0, base - (top + vh));
  return { base, vh, top, kb, kbOn: kb >= 120 };           // 120 是"这更像键盘还是更像地址栏伸缩"的门限
}

function syncViewport() {
  const m = viewportMetrics();
  const r = document.documentElement;
  r.style.setProperty("--vvh", m.vh + "px");
  r.style.setProperty("--vvt", m.top + "px");
  r.style.setProperty("--kb", m.kb + "px");
  r.classList.toggle("kb-on", m.kbOn);
}

/* 键盘动画期间要补几次；收起时把变量撤干净，交回 100dvh */
function syncViewportSoon() {
  [0, 140, 380].forEach(ms => setTimeout(syncViewport, ms));
}

function initViewportWatch() {
  const vv = window.visualViewport;
  if (!vv || !vv.addEventListener) return;
  vv.addEventListener("resize", syncViewportSoon);
  vv.addEventListener("scroll", syncViewportSoon);         // ⚠️ scroll 也要听：平移时只发它
}

/* 配套 CSS（整页尺寸基准 + 覆盖层都要带 top，流内元素最容易漏这个 top）：
  :root{ --vvh:100dvh; --vvt:0px; --kb:0px }
  #app{ height:var(--vvh,100dvh); top:var(--vvt,0); position:relative }
  .mask,.detail,.gate{ position:fixed; inset:0; height:var(--vvh,100dvh); top:var(--vvt,0) }
  .toast{ bottom:calc(var(--tab-h) + 30px + var(--kb,0px)) }
  html.kb-on .sheet{ padding-bottom:20px }      /* 键盘顶着时别再加安全区 */
*/

/* ---- 第二步：看得见的那条带子（可视区 ∩ 容器） ---- */
function visibleBand(containerRect) {
  const m = viewportMetrics();
  let top = m.top, bot = m.top + m.vh;                     // rect 是布局视口坐标，top 要一起用
  if (containerRect && containerRect.height > 0) {          // 再跟容器自己的可见范围求交
    top = Math.max(top, containerRect.top);
    bot = Math.min(bot, containerRect.bottom);
  }
  return { top, bot };
}

/* ---- 第三步：让控件完整落进那条带子 ---- */
function revealIn(scroller, el, pad) {
  if (!scroller || !el) return 0;
  const P = pad == null ? 12 : pad;
  const band = visibleBand(scroller.getBoundingClientRect());
  const r = el.getBoundingClientRect();
  let delta = 0;
  if (r.bottom > band.bot - P) delta = r.bottom - (band.bot - P);        // 下沿被盖 → 往下滚
  else if (r.top < band.top + P) delta = r.top - (band.top + P);         // 上沿跑出去 → 往回滚
  if (!delta) return 0;
  scroller.scrollTop = Math.max(0, scroller.scrollTop + delta);
  return delta;
}
```

**这一段为什么单独列出来 —— 三个"本地全绿、真机上坏"的坑**：

1. **`dvh` 不认软键盘。** `dvh` 是**布局视口**的比例尺，而软键盘**不改变布局视口** ——
   键盘顶到 508px 时，页面还以为自己有整机 844px 高，多出来的那截就被推到屏幕外、拖不回来。
2. **`position:fixed` 同样不认。** 还有更隐蔽的一条：`#app` 这类**流内元素**，
   光让它高度跟着可视区收还不够，**被平移时它自己不会跟着走** ——
   必须再给 `top:var(--vvt,0)`。**这条只有跑到"可视区被平移"那一档才会暴露，
   纯本地模拟怎么跑都是绿的。**
3. **`overflow:hidden` 的输入框，代码能移它、手指移不动它。** 如果它还跟着内容长高
   （实测长到 1125px 而可见的只有 508px），用户下拉是**一点反应都没有**的 ——
   而画面上完全看不出来。修法：`overflow-y:auto` + `max-height:calc(var(--vvh,100dvh) - 150px)`，
   并且**键盘一顶上来按新可视区把高度重收一次**。

> 这三条的正确验法：真浏览器里 stub `visualViewport`（同时给 `height` 和 `offsetTop`）
> 加一个假键盘覆盖层，跑**两档：平移 0 和 平移 200**。
> 判断"手指到底能不能拖"最省事的硬判据：**比较"滚前"和"滚后"两张截图的哈希** ——
> 哈希相同就是纹丝不动（代码滚得动、手指滚不动时正好是这个现象）。

**7.1 这两条为什么值得单独列出来**：它们在电脑浏览器上**完全看不出来**，只有真机才会暴露。而且「弹窗能左右滑」这个反馈在原项目里**来了两次** —— 第一次修表层没修对，第二次上真实浏览器逐状态量溢出、发现布局层溢出为 0，才摸到 iOS 自动放大这条真因。

> **同一个 bug 被反馈两次，就该换量具，而不是再猜一次。**
